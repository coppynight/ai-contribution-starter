# 两份改动都“完成了”，放在一起呢？

一个不需要先懂代码的**构造教学样例**：活动有 8 个名额，A 加入家庭报名，B 按原来的个人报名规则加入取消功能。两人各自检查自己的场景都能通过；但一家 3 人报名后再取消，剩余名额从 8 变成 5，再变成 6。完整取消应当恢复为 8。

这不是在指责某个贡献者，也不是一次真实用户事故。它说明：**单项工作的完成证据，不能代替改动组合后的验证。持续接纳贡献需要一套贯穿方向、交付、组合、反馈的机制。**

## 运行结果

需要 Python 3.10 或更新版本，无第三方依赖。在仓库根目录运行：

```sh
python registration-demo/verify.py
```

脚本实际调用模型和独立检查进程，逐项核对版本、检查项目与数量、预期值、实际值、通过状态和退出码，生成 [evidence.json](evidence.json)。少跑检查或因为其他原因失败，都不算演练通过。纯函数返回新的状态，不修改传入状态；验证还比较源码哈希，保证演练不修改源码。

| 阶段 | 实际经过 | 能说明什么 |
| --- | --- | --- |
| A 单独验证家庭报名 | 8 → 5，记录 3 人 | 家庭报名正确扣除名额 |
| B 在旧的个人场景验证取消 | 8 → 7 → 8 | 个人取消正确归还名额 |
| 两份改动的组合候选 | 8 → 5 → **6** | 完整取消没有恢复全部名额，组合检查失败 |
| 根据反馈修复后 | 8 → 5 → **8** | 按报名实际人数归还，旧检查与新增组合检查通过 |

同一检查入口可重复调用：

```sh
python registration-demo/check.py --version before
# 原有两个个人报名检查通过，退出码 0。

python registration-demo/check.py --version candidate
# 加上两个家庭场景检查，3 项通过、1 项失败，退出码 1（故意保留的错误候选）。

python registration-demo/check.py --version after
# 4 项检查通过，退出码 0；不传 --version 时默认检查这个修正版本。
```

`verify.py` 整体成功表示“上述通过和失败均符合演练预期”，不表示错误候选可以接纳。这里通过显式函数组合重现逻辑兼容问题，没有执行真实的多分支合并。

## 这个小项目里的贡献约定

约定可以放在现有任务说明或 PR 中，不需要再搭一套平台。

| 环节 | 本例中的具体动作 |
| --- | --- |
| 先确认方向 | 接纳家庭报名，但一条报名记录可对应多人；名额始终按人数计算。 |
| 明确责任与边界 | A 交付报名及人数记录；B 交付取消与名额归还；维护者负责确认组合后的规则，决定是否接纳。 |
| 贡献者带上交付依据 | 说明改了什么、沿用了什么假设、跑了什么检查，以及尚未验证的组合场景。A、B 的独立通过不能写成“所有流程都没问题”。 |
| 检查组合结果 | 在同一个候选版本走完“家庭报名 → 取消”，核对剩余名额应恢复为 8。 |
| 反馈后修正 | 将固定加 1 改为加上这条报名记录的实际人数，保留个人报名检查，新增家庭取消检查。 |
| 留下可复用入口 | 下一次贡献仍运行 `python registration-demo/check.py`，让已发现的问题进入后续反馈。 |

在 [model.py](model.py) 中可以直接对照 `cancel_legacy` 与 `cancel_fixed`：

```diff
-remaining=event.remaining + 1,
+remaining=event.remaining + booking.people,
```

这行差异是修复结果。让问题被发现、让贡献者收到反馈、让修复留下可重复执行的检查，才是本例要展示的机制。它不等于完整的生产系统，也不保证其他未检查场景正确。

## 与现有工程接上

本例只用四个 Python 文件和一个检查命令。迁移到自己的项目时，应复用已有任务、PR、测试和 CI 入口。完整的 [维护机制启动指令](../prompts/maintainer.md) 会引导 agent 先检查现状，再补齐影响后续贡献的缺口。

仓库的 `CI — Registration regression checks` 工作流在 push / pull request 时运行对照验证。另一个自动工作流运行 `python scripts/test_ci_contracts.py`，确认删除家庭回归检查、吞掉失败退出码等破坏会被验证器拒绝。工作流不会配置分支保护，不声称失败结果会强制阻止合入。

视频使用的数据接口位于 `evidence.json` 的 `visual_contract`，内容是实际模型运行值：`capacity=8`、`family_size=3`、`after_booking=5`、`broken_cancel=6`、`fixed_cancel=8`。每个阶段的事件、检查预期及实际结果位于 `stages`，可据此复查画面。
